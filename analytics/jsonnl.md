# Анализ Промптов 40-41 (JSONL) относительно стандарта CSV/TSV (24-39)

> Документ-спутник к `prompt3.md` от 11.09.2026. Фиксирует разбор пробелов Section 1b (JSONL) до расширения, таблицу соответствия с эталонным набором Промптов 24-39 (CSV/TSV) и итоговые решения по нумерации.

---

## 1. Исходное состояние Section 1b

До расширения Section 1b состояла из двух коротких промптов (40-41), каждый — на 4-5 строк задачи, без полей «Проблема», «Конфиг» и «Критерии готовности», которые стали стандартом после код-ревью CSV/TSV. По объёму и проработке это соответствовало уровню Промптов 22-23 (первая редакция TSV), а не уровню Section 1a. Иными словами, JSONL находился на стадии «есть заготовка базовой реализации», а все уроки, полученные при ревью CSV/TSV-хранилищ, в него не были перенесены.

Конкретно в Промпте 40 (базовая реализация) отсутствовали: требование streaming-парсинга (был риск, что реализация построит DOM каждой строки), правила маппинга полей JSON-объекта в колонки схемы, политика для вложенных структур, привязка к StorageFactory из Промпта 21 и любые критерии приёмки. В Промпте 41 (расширенные возможности) пункты «схема JSON с валидацией типов», «проекция полей» и «JSON Path» были сформулированы без правил и конфликтов между собой, а пункт «Сжатие (gzip, lz4)» противоречил решению Промпта 39 — отказу от gzip в пользу быстро распаковываемых кодеков через общую абстракцию CompressionCodec.

## 2. Эталон: что покрывает набор 24-39

Набор улучшений CSV/TSV, выработанный по результатам код-ревью, закрывает 13 системных тем, каждая из которых одинаково применима к любому RowBased-хранилищу:

1. **Корректность привязки данных к схеме** — маппинг по заголовку файла, fail-fast при несовпадении (Промпт 24).
2. **Стабильная идентичность строк** — row-id вместо позиционных индексов, корректность поиска после insertAt (Промпт 25).
3. **Различение NULL и пустой строки** — сентинел-семантика, round-trip без потери информации (Промпт 26).
4. **Диагностика ошибок загрузки** — координаты файл:строка:колонка, политики fail/skip (Промпт 27).
5. **Корректность записи** — экранирование служебных символов (Промпт 28).
6. **Детерминизм файлов** — фиксированные кодировка и переводы строк (Промпт 29).
7. **Crash-устойчивость записи** — temp+rename+fsync (Промпт 30).
8. **Мелкая корректность reader'ов** (Промпт 31).
9. **Режимы загрузки** — .table vs delimited, устранение двойного I/O (Промпт 32).
10. **Осмысленность блочного кэша** — реальный I/O или удаление слоя (Промпт 33).
11. **Параллельное чтение** — byte-offset pre-scan, устранение повторных сканов (Промпт 34).
12. **Деградация массовых операций** — O(n^2) при delete, deferred rebuild (Промпт 35), компактное представление строк (Промпт 36), инфраструктура (Промпт 37).
13. **Quality gate** — негативные и property-тесты (Промпт 38), сжатие через общий кодек (Промпт 39).

Для JSONL каждый пункт требует либо прямого переноса (адаптации под формат), либо осознанного решения «не применимо, потому что…». Ниже — полная карта.

## 4. Темы, уникальные для JSONL (нет аналогов в 24-39)

Помимо переноса паритета, формат требует решений, которых для CSV/TSV просто не существует. Они и составляют ядро «абстракционной» части расширения:

- **Абстракция JSON-парсинга (Промпт 42).** CSV/TSV парсят строку сами; в JSONL парсинг отдан библиотеке, и без единой точки входа библиотека «протечёт» во весь пакет storage. Введены JsonStreamParser/JsonStreamGenerator с реализацией по умолчанию на Jackson streaming (допустим бэкенд на Gson), запрет DOM-парсинга и общий JsonParserConfig (глубина вложенности, lenient-режим: Gson по умолчанию молча принимает NaN/Infinity — для СУБД это недопустимо).
- **Маппинг типов JSON ↔ типы СУБД (Промпт 43).** Шесть типов JSON против типизированных колонок: границы Integer/Long, потеря точности за 2^53, коэрция "1" → 1, даты из строк, поведение при дубликатах ключей. В CSV типы выводятся из схемы колонок; в JSONL без явного маппера каждый reader конвертирует по-своему.
- **Вывод и эволюция схемы (Промпт 44).** Самописный формат: набор полей может отличаться от строки к строке. Нужны режимы strict/inferred/hybrid, sidecar-файл схемы и fail-fast при смене типа поля.
- **Вложенность и массивы (Промпт 45).** flatten с dot-нотацией против json_column, конфликты имён, round-trip реконструкции, правила для массивов объектов — в CSV вложенность не выразима, поэтому аналога нет.
- **Append-режим записи и компакция (Промпт 49).** CSV/TSV всегда пишутся полным rewrite; для JSONL с большими объёмами дозапись с дельтой удалений и пороговой компакцией даёт порядок ускорения записи при сохранении crash-устойчивости.
- **Projection pushdown (Промпт 55, развитие 41).** Для CSV чтение только «нужных колонок» бессмысленно (строку надо распарсить целиком); JSON-токен-поток позволяет пропускать чужие поля почти без аллокаций — уникальное преимущество формата для аналитических запросов.

## 5. Решения по содержанию усиленных 40-41

- **Промпт 40** переписан в формате код-ревью: добавлены проблема, привязка к StorageFactory, требование streaming-парсинга, критерии приёмки (round-trip, потоковое чтение 100k строк, отсутствие special-casing в Table). Вложенность в базовой реализации — через JSON-колонку, с отсылкой к Промпту 45.
- **Промпт 41** переписан: «схема JSON» конкретизирована до валидации типов с диагностикой файл:строка:поле, «проекция» — до базы projection pushdown, «JSON Path» — до dot-нотации с отсылкой к правилам хранения вложенности. Пункт сжатия исключён из 41 и перенесён в Промпт 52 (общий CompressionCodec, ZSTD/LZ4/Snappy) — исходное упоминание gzip противоречило решению Промпта 39.
