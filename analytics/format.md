# Современные форматы хранилища для DieselDB

## Анализ текущей ситуации

**Текущие форматы:**
- CSV файлы для экспорта данных
- Java сериализация (.table) для полного состояния таблицы

**Проблемы:**
- Отсутствие ACID транзакций
- Хрупкая сериализация Java объектов
- Нет схемы данных
- Большой размер файлов
- Медленное чтение больших объёмов

---

## Apache Iceberg — Вердикт: ❌ НЕ ПОДХОДИТ

**Причины отказа:**
1. **Избыточная сложность**: Iceberg — распределённый табличный формат для Big Data (TB/PB масштабы)
2. **Зависимости**: Требует каталог (Hive/JDBC), 15+ зависимостей Maven, ~500MB heap
3. **Архитектура**: Batch-ориентирован, не предназначен для row-by-row операций
4. **Несоответствие**: DieselDB — embedded БД (~500KB кода), Iceberg — для кластеров Hadoop/Spark

### Условные обозначения:
- **Размер**: Относительный размер файла (меньше = лучше)
- **Чтение/Запись**: Относительная скорость (больше = лучше)
- **Типы**: Поддержка типов данных (✅ полная, ⚠️ частичная, ❌ нет)
- **ACID**: Поддержка транзакций
- **Внедрение**: 🟢 легко, 🟡 средне, 🟠 сложно, 🔴 очень сложно

## Рекомендуемые альтернативы для DieselDB

### 🏆 Топ-3 рекомендации

#### 1. Apache Parquet + JSON (для данных + метаданных)
```
<table>_data.parquet      — данные в колоночном формате
<table>.metadata.json     — схема, индексы, последовательности
```
**Преимущества:**
- Сжатие 70-90% относительно CSV
- Ускорение чтения в 3-5 раз (колоночный формат)
- Поддержка всех типов данных
- Богатая экосистема (Spark, Pandas, DuckDB)

**Недостатки:**
- Не подходит для частых обновлений отдельных строк
- Требует 2 зависимости Maven

#### 2. JSONL (JSON Lines) — текстовая замена CSV
```
<table>.jsonl             — каждая строка как JSON объект
<table>.schema.json       — схема таблицы
```
**Преимущества:**
- Человекочитаемый формат
- Поддержка типов данных и вложенных структур
- Простое внедрение (стандартные парсеры)
- Легко сжимается (gzip)

**Недостатки:**
- Больший размер чем бинарные форматы
- Нет ACID транзакций

#### 3. Apache Avro (для WAL — Write Ahead Log)
```
<table>_wal.avro          — лог изменений для crash recovery
```
**Преимущества:**
- Самодокументируемый формат (схема в файле)
- Поддержка эволюции схемы
- Компактный бинарный формат
- Идеален для последовательной записи

## Существуют ли улучшения CSV?

Да, существуют «эволюционировавшие» версии CSV:

### 1. CSV Schema + Types (Стандарт де-факто)
- **Суть:** Отдельный файл `.csv.schema` (JSON), описывающий типы колонок
- **Плюсы:** Совместимость со всеми парсерами, человекочитаемость
- **Минусы:** Нет стандартного способа экранирования сложных объектов
- **Оценка:** ⭐⭐⭐

### 2. TSV (Tab-Separated Values)
- **Суть:** Разделитель — табуляция вместо запятой
- **Плюсы:** Проблемы с запятыми в тексте исчезают
- **Минусы:** Табуляции в данных всё ещё ломают формат
- **Оценка:** ⭐⭐

### 3. NDJSON / JSONL (JSON Lines) — **ЛУЧШАЯ ЗАМЕНА CSV**
- **Суть:** Каждая строка — валидный JSON объект
- **Плюсы:** Есть типы данных, вложенность, стандартный парсер везде
- **Минусы:** Чуть больше размер (имена ключей повторяются)
- **Оценка:** ⭐⭐⭐⭐

### 4. CSVL (CSV with Length prefixes) — Гипотетический
- **Суть:** `len,type,value` вместо разделителей. Пример: `3,int,120|5,str,hello`
- **Плюсы:** Не нужно экранирование, очень быстрый парсинг
- **Минусы:** Нечитаем человеком, нет стандарта
- **Вердикт:** Не существует популярного стандарта

## Предлагаемая архитектура DieselDB v2.0

```
dieseldb/
├── system/
│   └── catalog.json          — каталог всех таблиц
├── tables/
│   ├── users/
│   │   ├── data.parquet      — основные данные
│   │   ├── metadata.json     — схема, индексы
│   │   └── wal.avro          — транзакционный лог (опционально)
│   └── orders/
│       ├── data.parquet
│       └── metadata.json
└── indexes/
    ├── users_id.bin          — бинарные индексы
    └── users_email.bin
```

## Итоговая рекомендация

**Для DieselDB оптимальный путь:**

1. **Краткосрочно**: Заменить CSV на **JSONL** + схема в JSON
   - Минимальные изменения кода
   - Сразу получаем типы данных и читаемость

2. **Среднесрочно**: Добавить **Apache Parquet** для хранения данных
   - Сжатие в 4-5 раз
   - Ускорение аналитических запросов в 3-5 раз

3. **Долгосрочно**: Внедрить **WAL на Avro** для надёжности
   - Crash recovery
   - Точка восстановления

**Не рекомендовано:**
- ❌ Apache Iceberg (избыточен для embedded БД)
- ❌ SQLite/LMDB (это уже готовые СУБД, а не форматы хранения)
- ❌ XML/YAML/TOML (не подходят для табличных данных)
