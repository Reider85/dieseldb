# Проблемы производительности O(n²) и хуже в проекте Diesel Database

## Найденные места с потенциальной квадратичной сложностью

### 1. Table.java - updateIndicesAfterInsert (строки 476-512)
**Описание:** Метод вызывается после вставки строки в таблицу с кластеризованным индексом.
**Проблема:** Вложенные циклы:
- Внешний цикл проходит по всем строкам после точки вставки: `for (int i = insertIndex + 1; i < rows.size(); i++)`
- Внутренний цикл проходит по всем индексам: `for (Map.Entry<String, Index> entry : indexes.entrySet())`
- Для каждого индекса выполняется `search()` который может быть O(log n) для B-tree, но вызывается многократно
**Сложность:** O(n × m × log n), где n - количество строк, m - количество индексов
**Рекомендация:** Пересмотреть стратегию обновления индексов после вставки. Вместо обновления всех последующих строк можно использовать более эффективную структуру данных.

### 2. SelectQuery.java - Nested Loop Join (строки 186-218)
**Описание:** При выполнении JOIN без возможности использования Hash Join.
**Проблема:** Классический nested loop join:
- Внешний цикл: `for (Map<String, Map<String, Object>> currentJoin : joinedRows)`
- Внутренний цикл: `for (int j = 0; j < joinRows.size(); j++)`
**Сложность:** O(n × m), где n и m - размеры соединяемых таблиц
**Рекомендация:** Улучшить эвристику выбора Hash Join, добавить другие алгоритмы (Merge Join, Index Join).

### 3. DeleteQuery.java - Обновление индексов после удаления (строки 95-112)
**Описание:** После удаления строк требуется обновить индексы для всех оставшихся строк.
**Проблема:** 
- Внешний цикл: `for (int i = 0; i < rows.size(); i++)`
- Внутренний цикл: `for (Map.Entry<String, Index> entry : table.getIndexes().entrySet())`
- Внутри выполняется `search()`, проверка `contains()`, `remove()` и `insert()`
**Сложность:** O(n × m × k), где n - количество строк, m - количество индексов, k - сложность операций индекса
**Рекомендация:** Использовать более эффективный механизм отслеживания смещений строк вместо полного перестроения.

### 4. Table.java - createUniqueClusteredIndex (строки 172-218)
**Описание:** Создание кластеризованного индекса на существующей таблице.
**Проблема:**
- Сортировка строк: O(n log n)
- Последующий проход для обновления всех индексов: `for (int i = 0; i < rows.size(); i++)` с вложенным `for (Map.Entry<String, Index> entry : indexes.entrySet())`
**Сложность:** O(n × m), где n - количество строк, m - количество существующих индексов
**Рекомендация:** Оптимизировать переиндексацию при создании кластеризованного индекса.

### 5. Table.java - readObject десериализация (строки 297-322)
**Описание:** Восстановление индексов при загрузке таблицы из файла.
**Проблема:**
- Внешний цикл по определениям индексов
- Внутренний цикл по всем строкам: `for (int i = 0; i < rows.size(); i++)`
- Для каждой строки выполняется `index.insert()`
**Сложность:** O(n × m × log n) для B-tree индексов
**Рекомендация:** Использовать пакетную вставку в индексы при загрузке.

### 6. SelectQuery.java - evaluateConditions при полном скане (строки 57-62, 223-229)
**Описание:** При отсутствии подходящего индекса выполняется полный скан таблицы.
**Проблема:** Для каждой строки проверяются все условия WHERE
- Цикл по строкам таблицы
- Вложенная проверка всех условий
**Сложность:** O(n × c), где n - количество строк, c - количество условий
**Рекомендация:** Развивать систему индексов для покрытия большего количества типов запросов.

### 7. UpdateQuery.java - массовое обновление без индексов (строки 27-32)
**Описание:** При обновлении множества строк без возможности использования индексов.
**Проблема:**
- Полный проход по всем строкам: `for (int i = 0; i < rows.size(); i++)`
- Проверка условий для каждой строки
**Сложность:** O(n × c) для поиска + O(u × m) для обновления индексов
**Рекомендация:** Добавить поддержку range scan через B-tree индексы.

## Общие рекомендации

1. **Оптимизация updateIndicesAfterInsert:** Вместо обновления всех последующих индексов при вставке в середину таблицы с кластеризованным индексом, рассмотреть использование структуры данных, поддерживающей эффективные вставки (например, skip list или tree-based storage).

2. **Улучшение JOIN:** Расширить логику выбора Hash Join, добавить Merge Join для отсортированных данных.

3. **Ленивое обновление индексов:** Отложить обновление индексов до момента чтения или использовать транзакционный подход с батчингом.

4. **Пакетные операции:** Для массовых вставок/удалений использовать пакетное обновление индексов вместо поштучного.

5. **Композиционные индексы:** Добавить поддержку составных индексов для ускорения сложных запросов с несколькими условиями.

## Проблемы сериализации

### 1. Table.java - Потеря данных indexDefinitions при десериализации

**Описание:** Поле `indexDefinitions` объявлено как `private final Map<String, String> indexDefinitions = new ConcurrentHashMap<>();` (строка 32) и не является `transient`.

**Проблема:** 
- При кастомной десериализации в методе `readObject()` (строки 277-325) поле `indexDefinitions` восстанавливается через `defaultReadObject()`, но затем используется в условии `if (indexDefinitions != null)` (строка 297).
- Однако, поскольку это `final` поле, оно всегда будет инициализировано при десериализации, но его содержимое может быть пустым, если оно не было корректно сохранено.
- Более критично: в методе `writeObject()` (строки 270-275) поле `indexDefinitions` явно не записывается, полагаясь на `defaultWriteObject()`. Это может привести к потере определений индексов.

**Сложность:** O(1) для записи, но потенциальная потеря данных приводит к O(n × m) при переиндексации из-за отсутствия информации о типах индексов.

**Рекомендация:** Явно сериализовать `indexDefinitions` в кастомном методе `writeObject()` и корректно восстанавливать в `readObject()`.

### 2. Table.java - Неэффективная перестройка индексов при десериализации

**Описание:** Метод `readObject()` (строки 277-325) выполняет полную перестройку всех индексов после загрузки таблицы.

**Проблема:**
- Для кластеризованного индекса: цикл `for (int i = 0; i < rows.size(); i++)` с вызовом `clusteredIndex.insert()` (строки 290-295)
- Для каждого дополнительного индекса: вложенный цикл `for (int i = 0; i < rows.size(); i++)` с вызовом `index.insert()` (строки 315-320)
- Каждая вставка в B-tree индекс имеет сложность O(log n), что дает общую сложность O(n × m × log n), где n - количество строк, m - количество индексов

**Сложность:** O(n × m × log n)

**Рекомендация:** 
- Использовать пакетную вставку в индексы при загрузке
- Рассмотреть возможность сохранения состояния индексов в сериализованном виде вместо их перестройки

---

### 3. Transaction.java - Глубокое копирование через сериализацию

**Описание:** Метод `cloneTable()` (строки 76-93) использует сериализацию/десериализацию для глубокого копирования таблиц в транзакциях.

**Проблема:**
- Полная сериализация таблицы с последующей десериализацией для каждого снимка таблицы
- При каждом вызове `snapshotTable()` или `updateTable()` выполняется полный цикл сериализации
- В сочетании с проблемой #2 (перестройка индексов при десериализации) это создает значительные накладные расходы
- Сложность для одной таблицы: O(n × m × log n) для десериализации + O(n) для сериализации

**Сложность:** O(n × m × log n) для каждого клонирования таблицы

**Рекомендация:**
- Реализовать более эффективный механизм глубокого копирования без полной сериализации
- Использовать copy-on-write подход для транзакций
- Кэшировать сериализованные данные между операциями

---

### 4. HashIndex.java - Сериализация ConcurrentHashMap

**Описание:** Класс `HashIndex` содержит поле `private final ConcurrentHashMap<Object, Set<Integer>> indexMap;` (строка 9).

**Проблема:**
- `ConcurrentHashMap` реализует `Serializable`, но его сериализация может быть неэффективной для больших индексов
- При сериализации сохраняется только текущее состояние, без оптимизации для структуры хэш-таблицы
- После десериализации может потребоваться реорганизация внутренней структуры HashMap

**Сложность:** O(k) где k - количество уникальных ключей в индексе

**Рекомендация:** Рассмотреть возможность использования обычного `HashMap` для индексов, которые не требуют потокобезопасности на уровне отдельных операций (поскольку таблица сама управляет блокировками).

### 5. Sequence.java - Сериализация AtomicLong

**Описание:** Класс `Sequence` содержит поле `private final AtomicLong currentValue;` (строка 10).

**Проблема:**
- `AtomicLong` реализует `Serializable`, но его внутреннее состояние может быть некорректно восстановлено в многопоточной среде после десериализации
- Поскольку `Sequence` используется для генерации автоинкрементных значений, важно гарантировать корректность состояния после загрузки

**Рекомендация:** Добавить кастомные методы `writeObject()` и `readObject()` для явного управления состоянием `AtomicLong` после десериализации.

### 6. DatabaseServer.java / DatabaseClient.java - Сериализация через сеть

**Описание:** Клиент-серверное взаимодействие использует Java Object Serialization для передачи запросов и результатов (DatabaseServer.java строки 181, 192, 203, 206; DatabaseClient.java строки 41, 43, 65).

**Проблема:**
- Java Serialization имеет известные проблемы с производительностью и безопасностью
- Большие результаты запросов могут создавать значительную нагрузку на сеть и память
- Отсутствие сжатия данных при передаче
- Нет контроля версий формата сериализации для сетевых сообщений

**Рекомендация:**
- Рассмотреть альтернативные форматы сериализации (Protobuf, Avro, JSON)
- Добавить сжатие для больших объектов
- Реализовать контроль версий протокола

### 7. BTreeIndex.java / BTreeClusteredIndex.java - Сериализация внутренней структуры Node

**Описание:** Внутренний класс `Node` в обоих B-tree индексах реализует `Serializable` (BTreeIndex.java строки 12-13, BTreeClusteredIndex.java строки 12-13).

**Проблема:**
- Сериализация всей древовидной структуры может быть неэффективной для больших индексов
- Каждый `Node` содержит `ArrayList` для ключей, дочерних элементов и индексов строк
- При десериализации воссоздается вся структура дерева, что может быть медленным для глубоких деревьев

**Сложность:** O(t) где t - общее количество узлов в дереве

**Рекомендация:**
- Рассмотреть возможность сохранения индексов в более компактном формате
- Использовать плоское представление дерева для сериализации
- Добавить возможность ленивой загрузки индексов

## Проблемы механизма транзакций

### 1. Transaction.java - Неэффективное глубокое копирование через сериализацию

**Описание:** Метод `cloneTable()` (строки 76-93) использует полную сериализацию/десериализацию Java Object Serialization для создания глубокой копии таблиц при снимках транзакции.

**Проблема:**
- При начале транзакции (`BEGIN TRANSACTION`) выполняется снимок всех таблиц: цикл по `tables.entrySet()` с вызовом `snapshotTable()` (Database.java строки 59-61)
- Каждый снимок таблицы вызывает `cloneTable()`, который выполняет полную сериализацию и десериализацию
- При десериализации происходит перестройка всех индексов (см. проблему "Неэффективная перестройка индексов при десериализации" выше)
- Сложность для одной таблицы: O(n × m × log n) где n - количество строк, m - количество индексов
- Для базы с k таблицами общая сложность начала транзакции: O(k × n × m × log n)

**Дополнительные проблемы:**
- `updateTable()` также вызывает `cloneTable()` при каждой модификации таблицы в транзакции
- Нет разделения между read-only и write транзакциями - все транзакции создают полные снимки
- При длинных транзакциях с множеством изменений хранится несколько версий таблиц в памяти

**Сложность:** O(k × n × m × log n) для начала транзакции + O(n × m × log n) для каждого обновления таблицы

**Рекомендация:**
- Реализовать Copy-on-Write (COW) подход вместо полного клонирования
- Использовать MVCC (Multi-Version Concurrency Control) для управления версиями строк
- Различать read-only и write транзакции, не создавая снимки для read-only
- Применять дельта-логирование изменений вместо хранения полных копий таблиц

### 2. Database.java - READ_UNCOMMITTED позволяет читать грязные данные других транзакций

**Описание:** Метод `getTableForQuery()` (строки 176-195) реализует логику выбора версии таблицы в зависимости от уровня изоляции.

**Проблема:**
- При уровне изоляции `READ_UNCOMMITTED` транзакция читает модифицированные данные из других активных транзакций (строки 182-190)
- Это приводит к чтению "грязных" данных (dirty reads), которые могут быть откачены другой транзакцией
- Код проверяет `otherTransaction.isActive()` но не проверяет, не находится ли другая транзакция в состоянии отката
- Нет механизма для обнаружения конфликтов при коммите

**Пример проблемы:**
```
Транзакция A: UPDATE table SET x=10 WHERE id=1 (не закоммичено)
Транзакция B: SELECT x FROM table WHERE id=1 → читает x=10 (грязное чтение)
Транзакция A: ROLLBACK
Транзакция B: имеет данные которых никогда не существовало
```

**Сложность:** O(t) где t - количество активных транзакций (для поиска модифицированных данных)

**Рекомендация:**
- Для `READ_UNCOMMITTED` использовать снимок на момент начала транзакции (как для других уровней)
- Реализовать правильную семантику уровней изоляции:
  - `READ_COMMITTED`: читать только закоммиченные данные
  - `REPEATABLE_READ`: гарантировать повторную читаемость в рамках транзакции
  - `SERIALIZABLE`: полная сериализуемость транзакций
- Добавить проверку конфликтов при коммите (optimistic/pessimistic locking)

### 3. Database.java - Отсутствие атомарности при коммите транзакции

**Описание:** Метод выполнения `COMMIT` (строки 64-81) последовательно обновляет таблицы и сохраняет их на диск.

**Проблема:**
- Коммит выполняется в цикле без атомарности: `tables.put()` → `saveToFile()` → `saveToSerializedFile()` для каждой таблицы
- Если ошибка произойдет в середине цикла (например, при сохранении на диск), база останется в несогласованном состоянии
- Часть таблиц будет обновлена в памяти, часть - нет
- Отсутствует WAL (Write-Ahead Log) для восстановления после сбоя
- Нет механизма отката частично выполненного коммита

**Пример проблемы:**
```
Транзакция модифицирует таблицы A и B
COMMIT:
  tables.put(A) ✓
  saveToFile(A) ✓
  saveToSerializedFile(A) ✗ (сбой диска)
  // tables.put(B) никогда не выполнится
// База в несогласованном состоянии: A обновлена в памяти, B - нет
```

**Сложность:** O(m × d) где m - количество модифицированных таблиц, d - сложность сохранения на диск

**Рекомендация:**
- Реализовать Write-Ahead Log (WAL) для записи изменений до применения
- Сначала записывать все изменения в WAL, затем применять атомарно
- Использовать двухфазный коммит:
  1. Фаза подготовки: записать все изменения в WAL
  2. Фаза коммита: применить изменения к таблицам
- Добавить checkpointing для ускорения восстановления

### 4. Transaction.java - Утечка памяти при длинных транзакциях

**Описание:** Класс `Transaction` хранит `originalTables` (снимок на начало транзакции) и `modifiedTables` (изменения) в памяти.

**Проблема:**
- Все снимки таблиц хранятся в памяти до завершения транзакции (commit/rollback)
- При длительной транзакции с множеством изменений память растет пропорционально количеству измененных таблиц
- `modifiedTables` использует `HashMap` без ограничения размера
- Нет механизма вытеснения старых версий на диск
- При большой базе данных и множестве параллельных транзакций возможна OOM (Out Of Memory)

**Сложность памяти:** O(k × n) где k - количество таблиц в транзакции, n - средний размер таблицы

**Рекомендация:**
- Реализовать ленивую загрузку снимков таблиц
- Выгружать старые версии таблиц на диск при нехватке памяти
- Использовать дифференцированное хранение (только дельты изменений)
- Добавить лимит на длительность транзакции и размер изменений
- Реализовать garbage collection для завершенных транзакций

### 5. Database.java - Race condition при доступе к activeTransactions

**Описание:** Поле `activeTransactions` объявлено как `ConcurrentHashMap`, но некоторые операции не являются потокобезопасными.

**Проблема:**
- Итерация по `activeTransactions.values()` в методе `createTable()` (строка 20) и `getTableForQuery()` (строка 183) может привести к `ConcurrentModificationException` если другая нить модифицирует мапу во время итерации
- Хотя `ConcurrentHashMap` поддерживает безопасную итерацию, snapshot iterator может не увидеть последние изменения
- В методе `createTable()` уведомление транзакций о новой таблице (строки 20-24) не атомарно с добавлением таблицы в `tables`
- Потенциальная гонка: одна нить создает таблицу, другая начинает транзакцию и может не получить уведомление

**Пример проблемы:**
```
Нить A: tables.put(newTable) 
Нить B: activeTransactions.values().forEach(tx -> tx.snapshotTable(newTable))
Нить C: beginTransaction() → может не увидеть новую таблицу в originalTables
```

**Рекомендация:**
- Использовать явные блокировки (`ReentrantReadWriteLock`) для критических секций
- Гарантировать атомарность операций "добавить таблицу + уведомить транзакции"
- Рассмотреть использование `StampedLock` для оптимистичного чтения
- Добавить синхронизацию при модификации `activeTransactions`

### 6. Database.java - Отсутствие обработки каскадных откатов

**Описание:** При выполнении `ROLLBACK` (строки 82-89) транзакция просто помечается неактивной и удаляется из `activeTransactions`.

**Проблема:**
- Нет проверки зависимостей между транзакциями
- Если транзакция A прочитала данные из транзакции B (при READ_UNCOMMITTED), и B делает rollback, A продолжает работать с несуществующими данными
- Отсутствует механизм обнаружения что прочитанные данные были откачены
- Нет уведомления зависимых транзакций об откате
- Возможна потеря данных или несогласованность

**Рекомендация:**
- Отслеживать зависимости между транзакциями (dependency graph)
- При rollback проверять есть ли транзакции, прочитавшие непрокоммиченные данные
- Реализовать каскадный rollback или блокировку зависимых транзакций
- Для READ_UNCOMMITTED документировать риски и возможно запретить в production

### 7. Transaction.java - Неэффективная работа с большими таблицами

**Описание:** Методы `snapshotTable()` и `updateTable()` клонируют всю таблицу независимо от количества измененных строк.

**Проблема:**
- Даже при изменении одной строки клонируется вся таблица со всеми индексами
- Для больших таблиц (миллионы строк) это создает огромные накладные расходы
- Время начала транзакции линейно зависит от размера всей базы данных
- Память расходуется неэффективно: хранятся полные копии неизмененных данных

**Сложность:** O(n × m × log n) для каждой операции snapshot/update независимо от объема изменений

**Рекомендация:**
- Реализовать fine-grained versioning на уровне строк
- Хранить только измененные строки в `modifiedTables`
- Использовать MVCC с версиями строк вместо копирования таблиц
- Добавить поддержку partial snapshots для больших таблиц

### 8. Database.java - Проблема фантомного чтения не решена ни на одном уровне изоляции

**Описание:** Текущая реализация не предотвращает фантомное чтение (появление новых строк в диапазоне).

**Проблема:**
- Даже при уровне `SERIALIZABLE` нет блокировки диапазонов или предикатов
- Транзакция может прочитать набор строк, другая транзакция добавит новую строку в диапазон, и первая транзакция при повторном чтении увидит "фантом"
- Отсутствует predicate locking или gap locking
- Уровни изоляции декларированы но не реализованы полноценно

**Рекомендация:**
- Реализовать gap locking для предотвращения фантомного чтения
- Добавить predicate locking для SERIALIZABLE уровня
- Использовать serializable snapshot isolation (SSI) алгоритм
- Документировать фактические гарантии каждого уровня изоляции

### 9. Database.java - Implicit transaction не откатывается при ошибке

**Описание:** В режиме autoCommit (строки 141-156) создается implicit транзакция для DML операций.

**Проблема:**
- При возникновении исключения во время `parsedQuery.execute(table)` (строка 144) транзакция не откатывается явно
- Блок `finally` только помечает транзакцию неактивной (строка 154)
- Изменения в таблице могут остаться в частично примененном состоянии
- Нет вызова rollback или очистки модифицированных данных

**Рекомендация:**
- Добавить явный rollback в catch блок для implicit транзакций
- Восстанавливать оригинальное состояние таблицы при ошибке
- Использовать try-with-resources для автоматического управления транзакцией
- Логировать ошибки с деталями для отладки
