# Проблемы производительности O(n²) и хуже в проекте Diesel Database

## Найденные места с потенциальной квадратичной сложностью

### 1. Table.java - updateIndicesAfterInsert (строки 476-512)
**Описание:** Метод вызывается после вставки строки в таблицу с кластеризованным индексом.
**Проблема:** Вложенные циклы:
- Внешний цикл проходит по всем строкам после точки вставки: `for (int i = insertIndex + 1; i < rows.size(); i++)`
- Внутренний цикл проходит по всем индексам: `for (Map.Entry<String, Index> entry : indexes.entrySet())`
- Для каждого индекса выполняется `search()` который может быть O(log n) для B-tree, но вызывается многократно
**Сложность:** O(n × m × log n), где n - количество строк, m - количество индексов
**Рекомендация:** Пересмотреть стратегию обновления индексов после вставки. Вместо обновления всех последующих строк можно использовать более эффективную структуру данных.

### 2. SelectQuery.java - Nested Loop Join (строки 186-218)
**Описание:** При выполнении JOIN без возможности использования Hash Join.
**Проблема:** Классический nested loop join:
- Внешний цикл: `for (Map<String, Map<String, Object>> currentJoin : joinedRows)`
- Внутренний цикл: `for (int j = 0; j < joinRows.size(); j++)`
**Сложность:** O(n × m), где n и m - размеры соединяемых таблиц
**Рекомендация:** Улучшить эвристику выбора Hash Join, добавить другие алгоритмы (Merge Join, Index Join).

### 3. DeleteQuery.java - Обновление индексов после удаления (строки 95-112)
**Описание:** После удаления строк требуется обновить индексы для всех оставшихся строк.
**Проблема:** 
- Внешний цикл: `for (int i = 0; i < rows.size(); i++)`
- Внутренний цикл: `for (Map.Entry<String, Index> entry : table.getIndexes().entrySet())`
- Внутри выполняется `search()`, проверка `contains()`, `remove()` и `insert()`
**Сложность:** O(n × m × k), где n - количество строк, m - количество индексов, k - сложность операций индекса
**Рекомендация:** Использовать более эффективный механизм отслеживания смещений строк вместо полного перестроения.

### 4. Table.java - createUniqueClusteredIndex (строки 172-218)
**Описание:** Создание кластеризованного индекса на существующей таблице.
**Проблема:**
- Сортировка строк: O(n log n)
- Последующий проход для обновления всех индексов: `for (int i = 0; i < rows.size(); i++)` с вложенным `for (Map.Entry<String, Index> entry : indexes.entrySet())`
**Сложность:** O(n × m), где n - количество строк, m - количество существующих индексов
**Рекомендация:** Оптимизировать переиндексацию при создании кластеризованного индекса.

### 5. Table.java - readObject десериализация (строки 297-322)
**Описание:** Восстановление индексов при загрузке таблицы из файла.
**Проблема:**
- Внешний цикл по определениям индексов
- Внутренний цикл по всем строкам: `for (int i = 0; i < rows.size(); i++)`
- Для каждой строки выполняется `index.insert()`
**Сложность:** O(n × m × log n) для B-tree индексов
**Рекомендация:** Использовать пакетную вставку в индексы при загрузке.

### 6. SelectQuery.java - evaluateConditions при полном скане (строки 57-62, 223-229)
**Описание:** При отсутствии подходящего индекса выполняется полный скан таблицы.
**Проблема:** Для каждой строки проверяются все условия WHERE
- Цикл по строкам таблицы
- Вложенная проверка всех условий
**Сложность:** O(n × c), где n - количество строк, c - количество условий
**Рекомендация:** Развивать систему индексов для покрытия большего количества типов запросов.

### 7. UpdateQuery.java - массовое обновление без индексов (строки 27-32)
**Описание:** При обновлении множества строк без возможности использования индексов.
**Проблема:**
- Полный проход по всем строкам: `for (int i = 0; i < rows.size(); i++)`
- Проверка условий для каждой строки
**Сложность:** O(n × c) для поиска + O(u × m) для обновления индексов
**Рекомендация:** Добавить поддержку range scan через B-tree индексы.

## Общие рекомендации

1. **Оптимизация updateIndicesAfterInsert:** Вместо обновления всех последующих индексов при вставке в середину таблицы с кластеризованным индексом, рассмотреть использование структуры данных, поддерживающей эффективные вставки (например, skip list или tree-based storage).

2. **Улучшение JOIN:** Расширить логику выбора Hash Join, добавить Merge Join для отсортированных данных.

3. **Ленивое обновление индексов:** Отложить обновление индексов до момента чтения или использовать транзакционный подход с батчингом.

4. **Пакетные операции:** Для массовых вставок/удалений использовать пакетное обновление индексов вместо поштучного.

5. **Композиционные индексы:** Добавить поддержку составных индексов для ускорения сложных запросов с несколькими условиями.

## Проблемы сериализации

### 1. Table.java - Потеря данных indexDefinitions при десериализации

**Описание:** Поле `indexDefinitions` объявлено как `private final Map<String, String> indexDefinitions = new ConcurrentHashMap<>();` (строка 32) и не является `transient`.

**Проблема:** 
- При кастомной десериализации в методе `readObject()` (строки 277-325) поле `indexDefinitions` восстанавливается через `defaultReadObject()`, но затем используется в условии `if (indexDefinitions != null)` (строка 297).
- Однако, поскольку это `final` поле, оно всегда будет инициализировано при десериализации, но его содержимое может быть пустым, если оно не было корректно сохранено.
- Более критично: в методе `writeObject()` (строки 270-275) поле `indexDefinitions` явно не записывается, полагаясь на `defaultWriteObject()`. Это может привести к потере определений индексов.

**Сложность:** O(1) для записи, но потенциальная потеря данных приводит к O(n × m) при переиндексации из-за отсутствия информации о типах индексов.

**Рекомендация:** Явно сериализовать `indexDefinitions` в кастомном методе `writeObject()` и корректно восстанавливать в `readObject()`.

---

### 2. Table.java - Неэффективная перестройка индексов при десериализации

**Описание:** Метод `readObject()` (строки 277-325) выполняет полную перестройку всех индексов после загрузки таблицы.

**Проблема:**
- Для кластеризованного индекса: цикл `for (int i = 0; i < rows.size(); i++)` с вызовом `clusteredIndex.insert()` (строки 290-295)
- Для каждого дополнительного индекса: вложенный цикл `for (int i = 0; i < rows.size(); i++)` с вызовом `index.insert()` (строки 315-320)
- Каждая вставка в B-tree индекс имеет сложность O(log n), что дает общую сложность O(n × m × log n), где n - количество строк, m - количество индексов

**Сложность:** O(n × m × log n)

**Рекомендация:** 
- Использовать пакетную вставку в индексы при загрузке
- Рассмотреть возможность сохранения состояния индексов в сериализованном виде вместо их перестройки

---

### 3. Transaction.java - Глубокое копирование через сериализацию

**Описание:** Метод `cloneTable()` (строки 76-93) использует сериализацию/десериализацию для глубокого копирования таблиц в транзакциях.

**Проблема:**
- Полная сериализация таблицы с последующей десериализацией для каждого снимка таблицы
- При каждом вызове `snapshotTable()` или `updateTable()` выполняется полный цикл сериализации
- В сочетании с проблемой #2 (перестройка индексов при десериализации) это создает значительные накладные расходы
- Сложность для одной таблицы: O(n × m × log n) для десериализации + O(n) для сериализации

**Сложность:** O(n × m × log n) для каждого клонирования таблицы

**Рекомендация:**
- Реализовать более эффективный механизм глубокого копирования без полной сериализации
- Использовать copy-on-write подход для транзакций
- Кэшировать сериализованные данные между операциями

---

### 4. HashIndex.java - Сериализация ConcurrentHashMap

**Описание:** Класс `HashIndex` содержит поле `private final ConcurrentHashMap<Object, Set<Integer>> indexMap;` (строка 9).

**Проблема:**
- `ConcurrentHashMap` реализует `Serializable`, но его сериализация может быть неэффективной для больших индексов
- При сериализации сохраняется только текущее состояние, без оптимизации для структуры хэш-таблицы
- После десериализации может потребоваться реорганизация внутренней структуры HashMap

**Сложность:** O(k) где k - количество уникальных ключей в индексе

**Рекомендация:** Рассмотреть возможность использования обычного `HashMap` для индексов, которые не требуют потокобезопасности на уровне отдельных операций (поскольку таблица сама управляет блокировками).

---

### 5. Sequence.java - Сериализация AtomicLong

**Описание:** Класс `Sequence` содержит поле `private final AtomicLong currentValue;` (строка 10).

**Проблема:**
- `AtomicLong` реализует `Serializable`, но его внутреннее состояние может быть некорректно восстановлено в многопоточной среде после десериализации
- Поскольку `Sequence` используется для генерации автоинкрементных значений, важно гарантировать корректность состояния после загрузки

**Рекомендация:** Добавить кастомные методы `writeObject()` и `readObject()` для явного управления состоянием `AtomicLong` после десериализации.

---

### 6. DatabaseServer.java / DatabaseClient.java - Сериализация через сеть

**Описание:** Клиент-серверное взаимодействие использует Java Object Serialization для передачи запросов и результатов (DatabaseServer.java строки 181, 192, 203, 206; DatabaseClient.java строки 41, 43, 65).

**Проблема:**
- Java Serialization имеет известные проблемы с производительностью и безопасностью
- Большие результаты запросов могут создавать значительную нагрузку на сеть и память
- Отсутствие сжатия данных при передаче
- Нет контроля версий формата сериализации для сетевых сообщений

**Рекомендация:**
- Рассмотреть альтернативные форматы сериализации (Protobuf, Avro, JSON)
- Добавить сжатие для больших объектов
- Реализовать контроль версий протокола

---

### 7. BTreeIndex.java / BTreeClusteredIndex.java - Сериализация внутренней структуры Node

**Описание:** Внутренний класс `Node` в обоих B-tree индексах реализует `Serializable` (BTreeIndex.java строки 12-13, BTreeClusteredIndex.java строки 12-13).

**Проблема:**
- Сериализация всей древовидной структуры может быть неэффективной для больших индексов
- Каждый `Node` содержит `ArrayList` для ключей, дочерних элементов и индексов строк
- При десериализации воссоздается вся структура дерева, что может быть медленным для глубоких деревьев

**Сложность:** O(t) где t - общее количество узлов в дереве

**Рекомендация:**
- Рассмотреть возможность сохранения индексов в более компактном формате
- Использовать плоское представление дерева для сериализации
- Добавить возможность ленивой загрузки индексов
