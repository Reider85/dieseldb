Отсутствие реального pushdown для фильтрации - код строит FilterPredicate для Parquet, но затем выполняет повторную
фильтрацию в Java, что сводит на нет преимущества pushdown.
Полное чтение всех колонок - метод groupToRow() обходит все колонки, а не только запрошенные, что увеличивает объем
читаемых данных.
Отсутствие индексов в Parquet - ColumnarTableStorage является read-only, при любых изменениях данные инвалидируются и
пересоздаются, что создает overhead для OLTP-нагрузок.
Неправильный порог переключения - запросы к таблицам от 10K до 1M строк классифицируются как OLAP и пытаются
использовать Parquet, которого еще не существует.
Высокий overhead сериализации - каждая строка требует создания HashMap, проверки типов и конверсии через сложное Parquet
API.
Дополнительный overhead ввода-вывода - использование ChannelInputFile и ChannelSeekableInputStream добавляет накладные
расходы по сравнению с простым чтением CSV.
Parquet эффективен для аналитики на больших объемах данных, но для OLTP-нагрузок (маленькие таблицы, частые мутации,
точечные запросы) он создает дополнительные накладные расходы без получения преимуществ. Деградация производительности в
3 раза объясняется использованием неподходящего механизма для типа рабочей нагрузки.
