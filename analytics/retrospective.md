# Ретроспектива реализации промптов из prompt.md

## Обзор

В рамках Phase 0 было реализовано **85 промптов**, охватывающих полный цикл разработки экспериментальной СУБД DieselDB: от парсинга SQL до транзакций, серверной архитектуры и CI/CD.

---

## Что получилось хорошо ✅

### 1. Синтаксический анализ SQL (Промпты 1-6)
- **SqlLexer** корректно токенизирует SQL: ключевые слова (регистронезависимые), идентификаторы (включая quoted `"MyColumn"`), строковые литералы, числа, операторы.
- **QueryParser** строит AST для SELECT, INSERT, UPDATE, DELETE, CREATE TABLE, CREATE INDEX.
- Поддержка литералов `TRUE`, `FALSE`, `NULL` с корректной обработкой (например, `WHERE flag = TRUE` не путает `flag` как литерал).
- Quoted-идентификаторы сохраняют регистр, обычные приводятся к верхнему регистру.

### 2. Транзакции и ACID (Промпты 41-50, 66-70)
- **Auto-commit** по умолчанию (ON), каждый DML автоматически коммитится.
- **BEGIN / START TRANSACTION** переключает в режим ручной транзакции (`autoCommit = false`).
- **COMMIT / ROLLBACK** завершают транзакцию, оставляя `autoCommit = false` (как в PostgreSQL).
- **SET AUTOCOMMIT = ON|OFF** работает корректно.
- **SELECT не влияет на транзакцию** — не вызывает автокоммит, даже если `autoCommit = true`.
- Интеграционные тесты подтверждают изоляцию: данные видны только после COMMIT, ROLLBACK откатывает изменения.

### 3. Трехзначная логика NULL (Промпты 51-60)
- Операторы сравнения (`=`, `!=`, `<`, `>`, `<=`, `>=`) с NULL возвращают `UNKNOWN`.
- `UNKNOWN` в WHERE интерпретируется как `FALSE` (строка исключается).
- **IS NULL / IS NOT NULL** работают независимо от трехзначной логики.
- Таблицы истинности для `AND` / `OR` с `UNKNOWN` реализованы:
  - `TRUE AND UNKNOWN` → `UNKNOWN`
  - `FALSE OR UNKNOWN` → `UNKNOWN`
  - `TRUE OR UNKNOWN` → `TRUE`
- Агрегатные функции (`SUM`, `AVG`, `MIN`, `MAX`, `COUNT(col)`) пропускают NULL; `COUNT(*)` считает все строки.

### 4. Серверная архитектура (Промпты 31-40)
- **DatabaseServer** с ThreadPoolExecutor (пул 100 потоков, очередь 100, AbortPolicy).
- **Таймаут сокета 30 секунд** — неактивные соединения закрываются.
- **Graceful shutdown**: ShutdownHook закрывает ServerSocket, прерывает потоки, ждёт завершения.
- Тесты подтверждают: 101-е соединение отклоняется, SIGTERM корректно завершает сервер.

### 5. Сборка и CI/CD (Промпты 21-30)
- **pom.xml** настроен: Java 17, JUnit Jupiter 5.10.0, maven-surefire-plugin.
- **CI workflow** (`.github/workflows/ci.yml`): запуск при push/PR в `main`, JDK 17 (Temurin), `mvn test`.
- Профиль Maven `test` для полного набора тестов (`mvn -Ptest test`).

### 6. Логирование (Промпт 72)
- SLF4J + Logback: замена `System.out.println` на logger'ы.
- Настроен rolling file appender (`logs/diesel.log`, 10 MB, 30 дней).

### 7. Документация (Промпты 73, 78-80)
- **PHASE0_CHANGES.md**: полное описание нововведений.
- **PERSISTENCE_README.md**: сериализация, `serialVersionUID`, `formatVersion`.
- **README.md**: инструкции по сборке, поддержка Java 17/21.
- **Changelog.md**: детальная история версий (до 2.7.59).

### 8. Инфраструктурные улучшения (Промпты 71, 74-77)
- Рефакторинг основных классов (`Table`, `Database`, `Transaction`).
- **CliRepl**: интерактивный CLI для ручного тестирования.
- Скрипты запуска (`start-server.sh`, `start-client.sh`).
- Benchmark report (`benchmark_report.md`) с метриками производительности.

## Что получилось не очень ⚠️

### 1. Производительность JOIN с OR в условии (Промпт 81)
- Запросы вида `JOIN ... ON ... OR ...` создают декартово произведение (600×600 = 360000 строк).
- **OutOfMemoryError** при сортировке таких результатов (тесты OrderByTest #27, #28).
- Hash Join отключается при наличии `OR` в ON, fallback на Nested Loop Join.
- **Workaround**: увеличен heap до 4GB в pom.xml, но это не решение проблемы.

### 2. GROUP BY (Промпт 82)
- При группировке по столбцу с уникальными значениями движок иногда возвращал 1 строку вместо N групп.
- Исправлено, но требуется дополнительная валидация на больших данных.

### 3. IN со списком значений (Промпты 83-84)
- `WHERE AGE IN (50, 51, 52)` возвращал 2 строки вместо 21.
- `WHERE NAME IN (...) AND BALANCE > 5000` игнорировалось, возвращались все 600 строк.
- Причина: некорректный разбор списка значений и фильтрация.

### 4. LIMIT/OFFSET (Промпт 85)
- `LIMIT 10 OFFSET 5` возвращал 0 строк вместо ожидаемых 2.
- В подзапросах LIMIT игнорировался (возвращал 600 строк вместо 10).

### 5. Масштабируемость тестов
- **QuantitativeTest** требует 4GB heap для выполнения (из-за cross join).
- Время выполнения некоторых запросов >1 минуты (например, FULL JOIN с сортировкой).
- CI может падать по таймауту или memory limit.

### 6. Частичная реализация промптов 81-85
- Промпты на исправление багов движка (81-85) **не были выполнены полностью**.
- QuantitativeTest всё ещё падает с OutOfMemoryError.
- Требуется дополнительная работа над оптимизацией JOIN и GROUP BY.

---

## Что не получилось ❌

### 1. Полное прохождение QuantitativeTest
- Тест проверяет точное количество строк для 150+ запросов.
- Из-за багов в JOIN, GROUP BY, IN, LIMIT/OFFSET часть проверок падает.
- **Статус**: 18 проверок failing (согласно prompt.md).

### 2. Оптимизация памяти для cross join
- Нет стратегии streaming или external sort для больших результатов.
- Увеличение heap — временное решение, не масштабируется.

### 3. SAVEPOINT (Промпт 50)
- SAVEPOINT явно исключён из реализации («игнорируй их»).
- В тестах нет упоминаний SAVEPOINT.

### 4. MVCC и Columnar Storage (План на Phase 1)
- Только обозначены в Plan.md как направления развития.
- Текущая реализация использует блокировки на уровне таблиц/строк.

## Оценка текущего уровня базы (в сравнении с СУБД)

| Критерий | DieselDB | Postgres | MySQL | H2 | SQLite | MSSQL |
|----------|----------|----------|-------|----|--------|-------|
| **SQL Parser** | 70% | 100% | 100% | 95% | 90% | 100% |
| **JOIN (INNER/LEFT/RIGHT/FULL/CROSS)** | 80% | 100% | 95%* | 90% | 85%* | 100% |
| **GROUP BY + Aggregates** | 75% | 100% | 100% | 95% | 90% | 100% |
| **Подзапросы** | 70% | 100% | 95% | 90% | 85% | 100% |
| **Транзакции (ACID)** | 85% | 100% | 90%** | 95% | 95% | 100% |
| **Изоляция (4 уровня)** | 80% | 100% | 70%** | 85% | 80% | 100% |
| **Индексы (BTree/Hash/Unique)** | 75% | 100% | 95% | 90% | 85% | 100% |
| **NULL-логика (3-valued)** | 90% | 100% | 100% | 95% | 95% | 100% |
| **Серверная архитектура** | 60% | 100% | 100% | 80%*** | 50%*** | 100% |
| **Производительность** | 40% | 100% | 95% | 70% | 75% | 100% |
| **Масштабируемость** | 30% | 100% | 95% | 60% | 50% | 100% |
| **Надёжность (Crash recovery)** | 50% | 100% | 90% | 70% | 80% | 100% |

\* MySQL не поддерживает FULL JOIN, SQLite не поддерживает FULL OUTER JOIN напрямую.
\** MySQL использует другую модель изоляции по умолчанию.
\*\* H2 и SQLite — встраиваемые БД без полноценного сетевого сервера.

### Итоговая оценка (средний процент):

| СУБД | % совместимости функционала |
|------|---------------------------|
| **PostgreSQL** | 100% (эталон) |
| **MSSQL** | ~98% |
| **MySQL** | ~92% |
| **H2** | ~85% |
| **SQLite** | ~82% |
| **DieselDB (Phase 0)** | **~67%** |

**Обоснование оценки DieselDB:**
- Реализован базовый SQL (SELECT, INSERT, UPDATE, DELETE, JOIN, GROUP BY, ORDER BY, подзапросы).
- Есть транзакции с 4 уровнями изоляции, NULL-логика, индексы.
- **Недостатки**: производительность (O(n²) алгоритмы), память (cross join), отсутствие оптимизатора запросов, ограниченный набор типов данных, нет VIEW/TRIGGER/STORED PROCEDURE, слабая отказоустойчивость.

## Выводы и рекомендации для Phase 1

### Приоритеты:
1. **Оптимизация JOIN**: добавить Merge Join, Index Join; улучшить эвристику выбора Hash Join.
2. **Исправление багов**: GROUP BY, IN, LIMIT/OFFSET (промпты 81-85).
3. **Управление памятью**: streaming для больших результатов, external sort.
4. **Оптимизатор запросов**: выбор плана выполнения, статистика по таблицам.
5. **MVCC**: замена блокировок на версионность для улучшения конкурентности.

### Долгосрочные цели:
- Columnar storage для аналитических нагрузок.
- Поддержка VIEW, TRIGGER, STORED PROCEDURE.
- WAL (Write-Ahead Logging) для crash recovery.
- Репликация и шардирование.

---

## Заключение

Phase 0 успешно заложила фундамент DieselDB: парсер SQL, транзакции, серверная архитектура, тесты, CI/CD. Однако для достижения уровня production-ready СУБД требуется значительная работа над производительностью, надёжностью и полнотой функционала. Текущий уровень (~67% от PostgreSQL) достаточен для образовательных и экспериментальных целей, но не для промышленных нагрузок.
