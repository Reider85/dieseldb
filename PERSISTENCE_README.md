# Выводы о готовности DieselDB к персистентности (чтение/запись таблиц с диска)

Дата проверки: 02.08.2026
Java: 21.0.11 LTS (проект заявлен на Java 17)

---

## 1. Ответ на вопрос: есть ли чтение таблиц с диска и запись на диск?

**Частично было.** Полноценное сохранение и восстановление было добавлено в ходе проверки.

### Что уже существовало (до изменений)
- `Table.saveToFile(String)` — экспорт таблицы в CSV (`<table>.csv`) при каждом DML за пределами транзакции и при коммите.
- Статический `Table.loadFromFile(Database, String)` — CSV-загрузка таблицы.
- Методы `saveToFile` / `loadFromFile` были объявлены в интерфейсе `TableStorage`.

### Чего не хватало (добавлено)
- Полноценного сохранения всего состояния таблицы (Java-сериализация в `<table>.table`):
  - `Table.saveToSerializedFile(String)` — сериализация таблицы целиком.
- Восстановления индексов после загрузки:
  - поле `Table.indexDefinitions` (`Map<columnName, indexType>`) сохраняется вместе с таблицей;
  - в `Table.readObject()` после перестройки кластерного индекса пересоздаются некластерные индексы (BTREE / HASH / UNIQUE) из `indexDefinitions`.
- Загрузки таблиц при старте сервера:
  - `Database.loadTablesFromDisk()` — сканирует каталог на `*.table` и загружает их;
  - `DatabaseServer.start()` теперь вызывает `database.loadTablesFromDisk()`.
- Явного сохранения всех таблиц:
  - `Database.saveTablesToDisk()` — сериализует все таблицы на диск.
- Очистки файлов при удалении таблицы:
  - `Database.deleteTableFiles(String)` удаляет `<name>.csv` и `<name>.table`;
  - вызывается из `dropTable()` и при удалении таблицы в транзакции.

### Когда теперь происходят сохранения
| Событие | CSV (`.csv`) | Полное состояние (`.table`) |
|---|---|---|
| INSERT / UPDATE / DELETE вне транзакции | да (каждый оператор) | нет |
| COMMIT транзакции | да | да |
| `saveTablesToDisk()` (в т.ч. при остановке сервера) | нет | да |
| Запуск сервера | — | загрузка всех `*.table` |

Это компромисс по производительности: писать `.table` на каждый DML нельзя — сериализация всей таблицы на каждый INSERT даёт O(n²) и замедляет вставку примерно в 15–20 раз (см. п. 4).

## 4. Найденная и устранённая проблема производительности

При первом варианте реализации `.table` сериализация выполнялась на каждый DML
(`Database.java`, ветка Insert/Update/Delete). Замеры:

- `saveToFile` (CSV): ~1–1.7 мс на 100 строк.
- `saveToSerializedFile` (`.table`): ~12.5–14.3 мс на 100 строк.
- 1000 вставок с сериализацией на каждую: **~55.7 с** (O(n²) — каждая вставка пере-сериализует всю таблицу + индексы).

Из-за этого `AdvancedTest` зависал (в логе ~434 вставленные строки за ~8 минут, таймаут 600 с).

**Исправление:** `.table` пишется только на COMMIT и в `saveTablesToDisk()`, на каждый DML остаётся только CSV. После исправления `AdvancedTest` проходит за разумное время (206 OK).

## 5. Известные проблемы (не относятся к персистентности, найдены ранее)

1. **PerformanceTest падает всегда (и до изменений):**
   `IllegalArgumentException: Unknown column: USERS.TRUE`
   в `SELECT NAME, AGE, BALANCE FROM USERS WHERE AGE < 30 AND ACTIVE = TRUE`.
   Парсер трактует `TRUE` как ссылку на колонку. Требует отдельного исправления.

2. **Регистр строковых литералов при вставке:**
   INSERT сохраняет строки в верхнем регистре (парсер нормализует запрос через `toUpperCase()`),
   а SELECT разбирает условие из исходного регистра. Пример:
   `WHERE NAME = 'Name2'` возвращает пустой результат, `WHERE NAME = 'NAME2'` — работает.
   Ошибка воспроизводится даже без персистентности (проверено отдельным прогоном).

3. **`USERS_PERF.table` (файл в репозитории) несовместим с текущей версией `Table`:**
   при добавлении поля `indexDefinitions` изменился неявный `serialVersionUID`, поэтому
   старая сериализация даёт `SEVERE: local class incompatible`.
   `loadFromFile` это обрабатывает корректно (возвращает `null`, таблица пропускается), но
   рекомендуется объявить явный `serialVersionUID` и поле версии формата.

## 7. Требования к сериализации (serialVersionUID и версия формата)

Все сериализуемые классы (`implements Serializable`) обязаны объявлять явное поле
`private static final long serialVersionUID = 1L;`. Явный `serialVersionUID` гарантирует
совместимость сериализованных данных при эволюции класса и предотвращает ошибку
`InvalidClassException: local class incompatible` при загрузке старых файлов.

Классы, у которых поле объявлено:
- `Table`
- `BTreeIndex` (включая внутренний класс `Node`)
- `BTreeClusteredIndex` (включая внутренний класс `Node`)
- `HashIndex`
- `UniqueIndex`
- `Sequence`
- `QueryMessage`

Текущая версия формата таблицы равна **1** (`Table.CURRENT_FORMAT_VERSION`).
Поле `Table.formatVersion` инициализируется значением `1` и сериализуется вместе с таблицей.
При загрузке (`Table.loadFromFile`) версия проверяется: если `formatVersion` не совпадает с
текущей, выбрасывается исключение `IllegalArgumentException`. Файлы таблиц имеют расширение
`.table`; при загрузке отсутствующего файла создаётся новая таблица с базовой структурой,
`formatVersion = 1` и корректным `serialVersionUID`.

> Важно: при любом изменении структуры сериализуемых классов, меняющем совместимость,
> увеличивайте `formatVersion` (и, при необходимости, обновляйте `CURRENT_FORMAT_VERSION`).
