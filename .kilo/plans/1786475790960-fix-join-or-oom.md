## Key Design Decision: Keep Nested Loop, Add Targeted Optimizations
Forcing hash join for OR queries would change query semantics (hash join on equality produces subset of nested-loop results). QuantitativeTest asserts exact 360000-row cross-product-like results for these queries. Therefore: **keep nested loop join for correctness**, but add targeted optimizations that reduce per-iteration cost and memory pressure without changing results.

/** Returns true if any ON condition has a logical OR conjunction. */
private boolean hasOrInOnConditions(QueryParser.JoinInfo join) {
    if (join.onConditions == null) return false;
    return join.onConditions.stream()
        .anyMatch(c -> "OR".equalsIgnoreCase(c.getConjunction()));
}

### Step 2: Other optimization — condition short-circuit improvement (SelectQuery.java)
Refine `evaluateConditions3vl` to add additional short-circuit opportunities using the existing `ThreeValuedLogic` utilities. The current code at lines 714-728 already has `orIsDetermined`/`andIsDetermined` checks; add a helper that pre-evaluates conditions with known constant values (e.g., `IS NOT NULL` is always true when the column is not null in the current row) to skip unnecessary sub-conditions.

```java
// New helper method after evaluateConditions3vl (~line 730):
private Boolean shortCircuitOrConditions(Map<String, Object> row,
        List<QueryParser.Condition> conditions, Map<String, Class<?>> combinedColumnTypes,
        Map<String, Table> tables) {
    // If any condition in the OR chain is determined TRUE by three-valued logic,
    // the whole OR is TRUE regardless of remaining conditions.
    Boolean result = evaluateCondition3vl(row, conditions.get(0), combinedColumnTypes, tables);
    for (int i = 1; i < conditions.size(); i++) {
        QueryParser.Condition cond = conditions.get(i);
        if (ThreeValuedLogic.orIsDetermined(result)) return true;
        result = ThreeValuedLogic.or(result, evaluateCondition3vl(row, cond, combinedColumnTypes, tables));
    }
    return result;
}
```
And use this in `evaluateConditions3vl` instead of the inline logic, reducing redundant evaluations.

Mitigation: keep index pre-filter as a hint that reduces candidate set but full condition evaluation still runs on all pairs; no state change.
